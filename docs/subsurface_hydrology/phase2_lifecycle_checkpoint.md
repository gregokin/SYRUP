# Accepted-boundary and closed-day physical checkpoints

The native CPU and CUDA lifecycle file interfaces are independently accepted at the bounded scope in [the CPU foundation receipt](phase2_lifecycle_checkpoint_cpu_acceptance.json) and [the combined CPU/CUDA receipt](phase2_lifecycle_checkpoint_cuda_acceptance.json). The CPU foundation receipt preserves its historical pre-adoption status; the later combined CPU/CUDA receipt records qualification after shared-hook reconciliation. They are native Python APIs in the still-unpublished Phase 2 source, not a new historical CLI mode.

Save an actually accepted, completed event Boundary or a CLOSED daily state of the current DailyHold. Save does not advance time, hand water back, reroute, publish a native storage journal, force quiet, or move the accepted head. Running occurrences, mid-day trials, pending storms and pending recession are explicitly refused. A resource limit is not completion.

The CPU module floating_lifecycle_checkpoint uses profile /1. Its CUDA counterpart floating_lifecycle_checkpoint_cuda uses /2-cuda and requires the expected device. Both need the caller’s static event factory, actual original topology, identity and explicit resource controls; loading also needs the external manifest digest returned by the writer. A closed-day file needs the matching evaporation partition. Historical profiles remain strict and are never rebound or migrated.

The files retain the genuine MAPLE bed, current layer water and Green–Ampt history, porous depth, surface depth and momentum, held properties, original terrain datum and carried routing origin. Event-local counters remain truthful. A closed-day restore preserves and recomputes execution/state/parent digests, revision, withdrawal sequence, rainfall cursor, accounting and moisture-frame identity. A fresh lineage receives its head last. The hold’s prior ledger and the day segment are added only once by a later handback.

The default returned object has only lineage, head, closed, kind and manifest_sha256. It deliberately releases the temporary continued-event carrier. Actual CPU and GPU weak-reference controls held the returned physical state alive while the carrier event, state, vertical, token, ledgers and both device phase arrays were collected; continuation still worked. This prevents unused sediment-phase arrays being retained by a soil-water restart.

NumPy, Numba, Dense and native Windowed storage are covered by bounded controls. Fresh-process recipes rebuild from static metadata plus the verified physical files without constructing an original bed, owner or property provider. Actual seven-day tests with real property updates and N=3 output preserve days 3 and 6 through restart. The output writer record remains separate; moisture snapshots are not themselves full restart files.

Memory models and admission tests are scoped to their actual operations. CPU deep/wide/windowed fixtures and GPU two-pool/default-reader/retention controls do not establish whole-catchment or whole-process memory fit. No scheduler, vegetation or wind state is included, and in-flight canonical rainfall-history proof remains outside these closed-parent files.
