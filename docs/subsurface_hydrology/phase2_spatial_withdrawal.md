# Phase 2 S2-B1.b — fixed-spatial CPU withdrawal and availability trials

> **Current status pointer (final documentation draft, 2026-11-13).** The text below is the author's original record and is preserved unchanged, including its "author-written / unrun" wording. Root's actual qualification of this component, with its exact tested scope and source identities, is in `phase2_spatial_withdrawal_acceptance.json`; where the two differ, that receipt governs. No whole-phase acceptance, publication or field validation is claimed by this page.

Status: author-implemented, **uncommitted, not independently accepted**, CPU only (NumPy and compiled Numba; no GPU/CuPy/NVRTC used). New module `src/maple_syrup/spatial_transpiration.py`; one minimal private change to `subsurface_transpiration.py`. A **pure trial** component: no exactly-once adoption, stale-proposal, LEAF, lifecycle, storm or restart claim; no geometry, water-fate, texture-to-property, K-averaging, root-frame or wetting-reset choice; three user physics questions unanswered.

## API

```
prepare_spatial_withdrawal(column, *, memory_budget_bytes, reserve_bytes=0, available_bytes_fn=None) -> SpatialWithdrawalOperator
estimate_spatial_withdrawal_memory(n_layers, n_cells, *, backend, operation="withdraw", reserve_bytes=0) -> SpatialWithdrawalMemory
spatial_layer_availability_m(operator, state, *, memory_budget_bytes, reserve_bytes=0, available_bytes_fn=None) -> (L, N) float64 depth [m]
spatial_withdraw(operator, state, requested_water_m, *, memory_budget_bytes, reserve_bytes=0, available_bytes_fn=None) -> SpatialWithdrawalResult
compiled_kernels() -> (withdraw, availability)      # the two process-wide compiled functions (functions only)
```
Law (unchanged): per active cell and layer `available = max(W − θres·dz, 0)`, `actual = min(requested, available)`, `W' = W − actual`, `unmet = requested − actual`, `scale = actual/requested` — a **dimensionless fulfilment fraction**, 0 where the request is 0 (`fulfillment_fraction` is an alias). The residual is a withdrawal floor, not a minimum inventory: zero or below-residual water is legal and no water is ever added. No clock advance (the result state has the SAME `t_s`), no evaporation, drainage, vertical exchange, plant demand, competition or root plasticity: LEAF owns the requests; SYRUP validates and debits the aggregate and returns the actuals. Inputs are the real `SpatialSoilColumn`/`SpatialSoilState`; `requested_water_m` is an exact `(L, N)` float64 C-contiguous NumPy array. Bounds are derived inline from the owner's raw maps in the accepted order: `res = θres·dz`, `sat = θsat·dz`, `satb = sat + coef·sat` (`coef = volume_roundoff_bound_m3(LAYER_OPERATION_TERMS, 1.0)`).

Budget fields and closure are those of `subsurface_transpiration.TranspirationBudget` (volumes over ACTIVE cells, area applied once, `n_terms = 3·L·n_active + 8`, MAPLE `volume_roundoff_bound_m3`); no new epsilon. Availability is a fresh `(L, N)` array, inactive cells 0; the input water is validated on EVERY cell (finite, `>= 0`, `<= saturation + tolerance`) with the common reason text; a refusal returns nothing.

## Binding (what it does and does not mean)

The operator is sealed (minted only by the factory; no direct construction, `replace`, copy or pickle), holds the real column object and its canonical input SHA-256 (parameters + mask + area), backend, namespace and `(L, N)`, and retains no copied bound map, mask or state. A `SpatialSoilState` carries `column_sha256`, dimensions, time and namespace but **no water-state generation and no owner-object identity**: a state of another owner object prepared from identical inputs is accepted; a state of different parameters or mask is refused. Two different water states can share metadata and clock (a withdrawal changes `W`, not the SHA or time), so an availability array or withdrawal result is **not** a generation-bound accepted receipt; a later integration must bind the accepted parent state/generation/occurrence. Legacy `SoilColumn`/`SoilColumnState`/`TranspirationOperator` and the spatial objects refuse each other with typed errors (the old guards were not changed); a CUDA owner is refused before any copy (the CUDA operator is a later slice); there is no fallback.

## One physical body per backend

* **NumPy** reuses `subsurface_transpiration._fused_numpy` through lazy per-layer row readers (a scalar for a scalar/shared layout, an `(N,)` row for a per-cell layout); the owner's bool mask is passed as it is.
* **Numba**: `subsurface_transpiration` now holds the SCALAR-ONLY inline decision helpers `_withdraw_available` and `_withdraw_cell` (validity flags, availability, min, unmet, fulfilment fraction) plus `_withdraw_init_rows`; the common compiled kernel and the spatial kernel both call them. Only the stores and the per-cell reduction-row bookkeeping are repeated structurally in the two loops (checked bit for bit against the common operator). Passing arrays into an inlined per-element helper made the common kernel 1.7–3× slower in a first attempt (measured), so the helpers take and return scalars. The spatial kernels are compiled for ONE explicit signature with READ-ONLY inputs (strided raw-map views, uint8 view of the mask), at the first preparation of a numba owner, outside hot calls; a failed build is a typed `SpatialLayerBackendUnavailableError` and a numba owner never runs the NumPy body. The spatial withdrawal stages the two bounds of one layer into two `(N,)` local rows (counted) because re-deriving them from strided maps inside the decision loop was ~2× slower.

## Memory (payload model, host; `estimate_spatial_withdrawal_memory`)

```
withdraw     outputs 4·L·N·8 (W', actual, unmet, scale) + rows 8·N·8 + scratch [N·8 + 3·64 (+ 6·L·N·8 for numpy, as the common NumPy body)]
             + bound rows [numpy: 6·N·8 lazy rows; numba: 2·N·8 staged local rows] + packet 64 + Python allowance 65536 + reserve
availability outputs L·N·8 + scratch [N (+ 4·N·8 numpy)] + [numpy: 6·N·8 lazy rows] + allowance + reserve
prepare      the withdrawal call on a 1 x 1 domain + allowance (JIT/compile excluded)
```
The caller's state and request and the owner's retained maps/mask are EXCLUDED; the payload formulas below are unchanged by correction01. `tracemalloc` evidence is incomplete for the Numba path (whether compiled-code heap blocks appear in a traced peak is not claimed portably): the two staged rows are counted from the SOURCE and checked with NRT allocation statistics (argument wrappers + exactly 2 rows, all freed, independent of N), and Root's L = 3, N = 50 001 trace (peak 8 804 416 B against outputs + rows ≈ 8 000 160 B, compatible with the 2N staged rows of 800 016 B, model 9 265 976 B) is consistent with them; rows are never double counted. Traced warm peaks are ≤ the model for both backends at (L, N) = (1, 50), (3, 2 000), (5, 20 000).  interpreter, JIT/compiler, allocator and whole-process memory are excluded; a reading is not a reservation. Admission (budget, reserve, reader) precedes every allocation, including NumPy row temporaries and failure paths; nothing raises a quota. The common estimate and operator are unchanged.

## Failure behaviour

Invalid water (non-finite, negative, above saturation + tolerance, in any cell incl. inactive), non-finite or negative requests and positive requests on inactive cells are refused with `SubsurfaceError` before anything is published; the state, request, mask and maps are never written; the clock is exact. Finite accepted parameters can still give a global volume (depth sum × cell area) or the closure scale `before + requested` that FP64 cannot represent (e.g. area 1e308 with all cells at W = q = 0.2 m): such a call is refused with a typed `SubsurfaceError` ("not representable in FP64 … nothing was published") on both backends BEFORE the strict conservation helper is called — never clipped, approximated or reported as a raw helper error; the valid arithmetic, coefficient and `n_terms` are unchanged. The reported reasons keep the common operator's `max` aggregation over per-cell flags, so a refusal caused by several different invalid cells may name only some of them (preserved, not fixed). The stage prefix of the message is `spatial_withdraw`/`spatial_layer_availability_m`; the reason text is the common text.

## Checks (CPU; `tests/phase2_spatial_withdrawal/`, 106 tests)

Per-column bit-exactness against the accepted common operator (NumPy and Numba; L = 1/2/3/5; zero, at-floor, below-floor, saturated, mixed and random water; requests 0/under/equal/over/random; masks incl. inactive columns; scalar/shared/cell layout combinations); NumPy and Numba owners bit-equal on every array; the dyadic example (W = [25, 200]/1024, q = [50, 50]/1024 → remaining [0, 150]/1024, scale [0.5, 1], aggregate delivery 75 %); availability against its definition and against the actual of an oversized request; typed refusals with no mutation; cross-refusals; state-binding semantics (input SHA, not object identity); genuine compiled kernels (nopython, no fastmath, one read-only-typed signature) and no NumPy fallback; admission boundaries before any allocation; traced warm peak within the model; NRT block count (2 staged rows); ownership/release; source scope (no second solver). The B1.a common-reader tests, the CUDA shared-body and spatial CUDA suites, and every earlier suite pass unchanged.

Timings (single thread, small kernels; `s2_b1_b_timings.json`). **Scopes, corrected (correction01):** (1) the COMMON Numba body before/after the scalar-helper split was timed interleaved on IDENTICAL data in the author's script (ratios 0.995–1.011 for L = 3/5/9 at 10 000/200 000 cells) and independently by Root at 131 071 cells (arrays and rows exact; ratios 0.987 / 1.022 / 0.9996 / 0.9726 for L = 1/3/5/9); small 8 192-cell timings vary in both directions between runs, so neither "no overhead" nor "a regression" is claimed universally. (2) The spatial-vs-common rows of the author's benchmark are **illustrative distinct workloads, not a matched cost comparison**: the common operator there used separate uniform properties, `cw = min(w, 0.9·saturation)` and `cq = 0.1·q`, so no overhead ratio between the spatial and the common operator may be derived from them. (3) Spatial Numba vs spatial NumPy (same spatial owner data) was about 2–2.4× faster for Numba at these sizes. Cold build of the two spatial kernels ≈ 1.1 s. No storm, LEAF, moving-bed or scaling claim.
