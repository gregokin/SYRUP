# Independent read-only review of Root's scientific-control scripts (stage 3)

Reviewed: `root_experiment_run.py`, `root_decimal_control.py`, `root_run_decimal.py`, `root_result_audit.py`, the launch configs (`root_observed_cpu_config.json`, `root_observed_cuda_config.json`, `root_decimal_config.json`), `root_run_seal.json`, `actual_cpu/*`, `root_decimal_summary.json`, `root_result_audit.json`, `root_observed_cuda_runs/*`. Nothing was edited. Supporting probes (stdlib/Fractions, no model run): `stage3_probes/review_probe.py` → `stage3_probes/review_probe_result.json`.

## Summary
No hidden physics, fitting or tuning was found: the only data-driven step is the frozen selection in `finalize_heldout.py`, and I re-derived it independently. The Decimal control and the CSV audit are sound for what they test. I found **one confirmed factual defect in a Root evidence file** and several coverage gaps / latent risks that matter mainly for the GPU repeat. None invalidates the CPU numbers.

## Confirmed issues
1. **`root_citations.json` names the wrong precipitation product.** It cites "precipitation (DP1.00006.001)" but every precipitation file used is `DP1.00045.001` (tipping bucket, `…TIPPRE_30min…`, as pinned in the inventory; throughfall is DP1.00046.001). The report corrects the reference text in its reference list (the evidence file is untouched); Root may wish to fix the source list.
2. **Audit/Decimal "70 digits" is asserted, not enforced.** `decimal_check` writes `'precision_decimal_digits': 70` as a constant and never reads the active context; precision is correct only because both callers wrap the call in `localcontext().prec = 70`. Called any other way it would run at 28 digits and still claim 70. Latent (current outputs are right), cheap to harden (`getcontext().prec` recorded/asserted).

## Coverage gaps (checks that are not in the scripts; I closed several in the probe)
3. **`root_result_audit.py` takes the sensor depths from the result** (`prep['sensor_depths_m']`), so the corrected-depth join is not independently audited there. Probe: depth table rows for JORN plot 4 (0.058/0.158/0.258) and MOAB plot 2 (0.055/0.155/0.255) equal the exported depths. ✔ (independent)
4. **The anchor rule is not audited.** The script checks that t0 is a passing joint observation, not that it is the first joint passing END strictly after run start + 72 h inside the stated rain-free run. Probe (raw CSV, rational QA): first joint END after exclusion = 2025-04-08T22:00Z (run 403.5 h), 2025-04-26T06:30Z (199.0 h), 2025-05-22T03:30Z (309.0 h); all equal the driver anchors. ✔
5. **PET is not independently recomputed** (the Decimal control and the audit consume the exported `pet_mm_day`). Probe: Hargreaves with the EcoHyD constants (0.0023(T̄+17.8)√(Tmax−Tmin)·Ra, dr, declination, sunset angle, `15.392`) from the exported Tmin/Tmean/Tmax, calendar date and the config latitude reproduces every exported PET with relative difference 0.0 in all three windows. ✔ Weather-E units are consistent: PET mm/day → ÷1000 m/day; the native step uses m/s × 86 400 s (Decimal control uses the same conversion).
5b. **Persistence, skill and the pooled RMSE are not audited by Root's script** (only per-scenario scores are). The report builder recomputes them from the exported targets/layer states and asserts equality with the stored values (all pass).
6. **Continuity of the weather windows / day-ends is not checked** against the anchor (the audit trusts the exported `window_start_utc`). The report builder asserts day-ends and weather windows are consecutive 24 h and `t_s = 86400·k`; passed.
7. **Decimal control scope.** It re-solves the evaporation + sequential-pair diffusion branch with water states and evaporation compared; it does not compare `diffusion_m`, `evaporation_unmet_m`, the cumulative budget or time, and (by construction, FC = sat) it cannot exercise gravity/drainage/closed-bottom — it asserts those are inactive. It starts from the driver's binary64 initial water (`plan.initial_layer_water_m`) and binary64 inputs (`D.from_float`), not an exact rational initial integral; the audit separately checks the initial integral against an exact Fraction integral (≤ 3 ulp of the layer value). Together the chain is closed, but the Decimal result alone is "same binary inputs, high-precision arithmetic", not "decimal-literal reference".
8. **Bound semantics.** The state error after day k (accumulated over days) is compared with a single-step native bound (`volume_roundoff_bound_m3(19, max water)`). Observed ratios ≤ 0.031, so there is no practical issue, but the bound is not a rigorous cumulative bound.
9. **`initial_fraction_integral_max_error_m` is identical (2.6020852139652106e-18) in all three windows.** This is float quantisation (three ulps of a ~6·10⁻³ m layer water), not a per-window measurement; my exact comparison against the binary edges gives window-dependent errors ≤ 1.4·10⁻¹⁸ m per layer (≤ 2.6·10⁻¹⁸ against decimal-string edges). Not a defect; avoid reading it as site-dependent.

## Scientific-control questions asked by Root
* **Hidden physics/fit:** none in the four scripts. The frozen selection (`finalize_heldout.py`) = minimum primary overall RMSE over `d…_E…_open`, ties → smaller E then smaller d; re-derived independently from the exported states: best pair d = 0, E = 0.5, one scenario at the minimum (no tie), equal to Root's finalize log; held-out lists are the 3 deduplicated scenarios. Held-out configs differ from the templates only in `scenarios` and the `heldout_status` text.
* **Score counts and clock:** valid targets per layer (8/10/10, 4/4/3, 6/4/4) and joint counts (8, 3, 3) agree with the audit and with my independent recomputation of every score/persistence; `t_s` = 86 400·k; day-end times are 24 h apart.
* **First backend is Numba:** configs list `['numba','numpy']`; the stored scores/trajectories are the Numba run. NumPy and Numba agree exactly in all 62 scenarios (maximum absolute difference over every trajectory array 0.0, including d > 0), far inside the inherited 2e-12/1e-14 contract.
* **Seal:** 52 files (data, depth table, driver/importer, tests, configs, finalize, `root_experiment_run.py`, `root_decimal_control.py`, decision notes) are re-hashed before and after the runs. The training config equals the frozen config byte for byte. `root_run_decimal.py` and `root_result_audit.py` are not sealed (post-run tools).

## Risks for the GPU repeat (not defects today)
a. `runtime.json` records only `numpy, numba, cupy-cuda12x, scipy`; a differently named CuPy distribution (or CUDA 13 wheel) would be missing, and no device name/UUID, driver or CUDA runtime version is recorded. Add `cupy` runtime/device properties inside the CUDA child.
b. `root_result_audit.py` and `root_run_decimal.py` hard-code `actual_cpu`; the GPU outputs need a parameterised path and must not overwrite `root_result_audit.json` / `*_decimal_control.json` (they are written without an existence check).
c. In CUDA mode the first backend is `cuda`, so the stored scores come from the CUDA trajectory; held-out parameters still come from the CPU training result (correct). Report the CPU-vs-CUDA score differences explicitly and keep the bitwise-at-d = 0 expectation as a reported outcome, not a pre-filter.
d. `out.mkdir(exist_ok=False)` plus no `completion.json` on exceptions is a safe design, but a failed partial run leaves a directory that blocks reruns until moved.
e. `SYRUP_OBSERVED_RUN_MODE` is not validated (any value other than `cuda` takes the CPU branch and names the output `actual_<mode>`).
f. GPU status: `root_observed_cuda_runs/prelaunch_refusal.json` records NOT_LAUNCHED (GPU0 guard refused; no child, no context). The report states GPU observed-profile qualification as pending and reads `data/` for any completion record.
