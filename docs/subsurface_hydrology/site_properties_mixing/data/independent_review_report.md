## Decimal control `root_decimal_control.py` — applicability to these dry, sub-FC cases
Applicable, and it was run on all 12 stored configs/results (CPU and CUDA, 56/56/3/3/3/3 scenarios each): max water error 2.2e-18 m, ≤ 2.9 % of the inherited FP64 bound, drainage and surface return asserted 0.
* Why it fits: it re-implements only the declared top-layer evaporation (residual cap, quadratic stress multiplier) and donor-depth diffusion (d·K_if·h_donor, exponential relaxation, donor availability and receiver-saturation caps), and **asserts** each day-start state is below FC (line 28) and `drainage == surface_return == 0` (line 45); in these cases FC ≈ 0.37–0.40 ≫ θ ≤ 0.07, so the omitted gravity branch is genuinely inactive and the assertion would fail loudly if a future case approached FC. It exercises the residual cap (E ≥ 1) and, for MOAB, the stress branch, and it reads K from each config, so it checks that the column honours the H or G coefficient actually written (H/G effects ~1e-5 in θ are far above its 1e-18 m error).
* Limits to state: (i) 70-digit precision tests the binary64 solver against exact arithmetic on the same float64 inputs; it is not independent of the team's reading of the native formulas, and it is an equation control, not a validation of hydrology; (ii) it does not test the K derivation (covered by the helper tests against the earlier audit values, rel 1e-12); (iii) its tolerance is the inherited bound (≈ 1e-16 m here), so it cannot see relative errors smaller than about 1e-14 of the stored water; (iv) initial water is taken from the result's own plan (validated separately by the prepared-input equality with the historical results); (v) it covers the day-start sub-FC state only, which is sufficient here because evaporation and donor-to-receiver exchange cannot raise a layer above its donor's θ < FC.
